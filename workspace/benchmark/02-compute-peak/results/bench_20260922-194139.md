## 关键结论速览

- ALU 占用率拐点：`global ≈ 114688`（每硬件 lane 16 个 work-item）。g=7168 时只有 10.1 TFLOPS = 峰值的 20% —— **这就是「低占用率测到延迟而非吞吐」**。
- ALU 向量宽度扫描 [(1, 34.8), (2, 45.5), (4, 52.8), (8, 50.7), (16, 51.3)]：VEC=4 最佳（52.8 TFLOPS），VEC≥4 后基本拉平 → 该循环 **issue 受限**，继续加宽向量不再有收益。
- XMX 占用率拐点：**每 EU ≥8 个 sub-group（global ≥ 57344）**才能打满 XMX；1 sg/EU 时仅 118 TFLOPS。低于拐点时「工作量翻倍、耗时不变」是**延迟受限的正常表现**，不是编译器消循环。
- XMX 原始 DPAS 峰值：bf16 **355 TFLOPS**、int8 **710 GOPS**（int8/bf16 = 2.00×，正好是 K=32 vs K=16 的 2×）。折算 = 256 MAC/clk/EU。
- **oneDNN GEMM（第三方、可信口径）**：fp32 22.1 TFLOPS（= 公式标称 22.2 的 100%）、bf16 225.9（= 自研 DPAS 峰值的 64%）、int8 416 GOPS（= 59%）。oneDNN bf16 仍是产品常引用值 176 TFLOPS 的 1.28×。
- ⚠ **口径冲突（本目录最重要的待解问题）**：公式标称 FP32 = 22.22 TFLOPS；oneDNN GEMM 实测 22.2（恰好 100% 公式值）；但自研纯 FMA 探针实测 50.8 TFLOPS（2.28×）。两者不能同时为真 —— 主频已锁定、满载不降频，嫌疑集中在「FLOP 计数口径」或「clinfo 的 EU 数」。**判读纪律：以 oneDNN 为可信下界，自研探针为待验证上界。**
- 公式标称 FP32 ALU 峰值 = 448 EU × 16 lane × 2 × 1.55 GHz = **22.22 TFLOPS**；XMX 公式标称 = 256 MAC/clk/EU → **356 TFLOPS (bf16)** / **711 GOPS (int8)**。所有自研探针均已通过「饱和区 ×2 工作量 → ×2 耗时」自校验。
